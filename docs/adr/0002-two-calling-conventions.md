# 两种调用约定并存，不做「每个动作都写成程序」

PTC 的收益来自把多步工具调用压进一次执行、中间态不回上下文；但编码工作里最常见的单步操作（读一个文件、改一处、跑一条命令）用程序包一层，只是多付一次解析与子进程启动的开销。因此本项目**同时**暴露两种调用约定，由模型按活的性质选：单步走直通调用，多步、需循环或需分支的活走程序化调用。DSH 自己在 PTC 设计笔记里否决过"全程程序化"（*"forcing every edit through a program taxes the common case"*），但它的呈现模式是 per-agent 二选一；我们在 WorkBuddy 的工具层可以两种都给，没有必须继承那个互斥的理由。

## Considered Options

- **全程程序化（Cloudflare Code Mode 的忠实形态）** —— 覆盖最彻底、单一调用约定、模型只需学一种写法。否决：给最常见的操作上税，且 DSH 官方在同一取舍上已经否决过它。
- **跟随 DSH 的 per-agent 互斥模式** —— 与上游保持一致，行为可预期。否决：工具面由我们这层自己定，继承这个约束换不到任何东西。

## Consequences

- 模型同时看到直通工具与 `run_program`，工具描述上下文翻倍。若实测发现这部分本身成了负担，改为按需加载而不是砍掉某一条约定。
- 「全程用 PTC」这个说法在本项目里被**禁用**——它同时能指"每个动作都写成程序"和"这条通道全程可用"，两者差别巨大。要写明是哪一个。
- 验收时要能观察到这个分岔真的生效：同一个任务里既有直通调用，也有一次做完多步的程序化调用。
- 这条决定**依赖于** ADR-0001（dsh 不出模型）。如果哪天 dsh 的 agent 真的参与进来，这里的取舍要重做。
